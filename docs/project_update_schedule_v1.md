# MidiPlayerプロジェクト分析と改修計画 (v3)

このドキュメントは、MidiPlayerプロジェクトの包括的な分析を概説し、主要な問題を特定し、リファクタリング、機能強化、および近代化のための段階的な計画を提案するものです。

## 1. 所見の概要

`codebase_investigator`エージェントは、プロジェクトのソースコードと既存のドキュメントの徹底的な分析を実行しました。主要な所見は以下の通りです。

### 問題点と改善領域

1.  **開発リソースの集中:** `MidiPlayer.Win64`アプリケーションは、`MidiPlayer.Droid`アプリケーションと比較して機能が著しく不足しています。今後の開発はAndroidプラットフォームに集中するため、**Windows UIの開発は凍結します。**
2.  **テストの品質とカバレッジ:** `MidiPlayerTest`内の既存のテストは、脆く、ステートフルであり、単体テストというよりは統合テストに近いです。特定の外部ファイルやタイミング（`Sleep(3000)`）に依存しているため、信頼性が低くなっています。カバレッジは低く、`EventQueue`メカニズムのようなコアロジックを検証していません。
3.  **グローバルな状態と静的クラス:** 静的クラス（`EventQueue`, `Mixer`, `Env`, `Synth`）の多用はグローバルな状態を導入し、アプリケーションを分離してテストすることを困難にし、モジュール性を低下させています。これは重大なアーキテクチャ上のコードの臭いです。
4.  **依存関係のリスク:**
    *   **ネイティブライブラリ:** プロジェクトは、プリコンパイルされたネイティブFluidSynthバイナリ（`.dll`, `.so`）に依存しています。これらのビルドとデプロイのプロセスは文書化されておらず、脆弱である可能性があります。
5.  **CI/CDの欠如:** 継続的インテグレーションまたは継続的デプロイメントのパイプラインの形跡がありません。これにより、開発が遅れ、リグレッションのリスクが高まります。
6.  **UI/UXの非一貫性:** Android UIでは、「Send to Synth」ボタンを明示的に押す必要があります。これはイベントの殺到を防ぎますが、理想的なユーザーエクスペリエンスではありません。
7.  **構成管理:** `Conf.cs`クラスには、構成ファイルの場所を特定するためのプラットフォーム固有のコードが含まれています。これは、より堅牢でプラットフォームに依存しないように抽象化できます。
8.  **コードのドキュメント:** `/docs`フォルダ内の分析ドキュメントは優れていますが、ソースコード自体には、実装の詳細の背後にある*理由*を説明する詳細なコメントが不足している可能性があります。

## 2. 提案される実行可能なタスク

所見に基づき、以下のエピック、ストーリー、およびタスクが提案されます。

- **エピック1: アーキテクチャのリファクタリング**
    - **ストーリー1.1: 静的クラスをシングルトンにリファクタリング**
        - **タスク1.1.1:** `EventQueue.cs`を静的クラスからシングルトンインスタンスにリファクタリングする。
        - **タスク1.1.2:** `Mixer.cs`をシングルトンインスタンスにリファクタリングする。
        - **タスク1.1.3:** `Env.cs`と`Conf.cs`を単一の構成インスタンスとして管理されるようにリファクタリングする。
        - **タスク1.1.4:** `Synth.cs`をインスタンス化可能なクラスにリファクタリングし、シングルトンとして管理する。
    - **ストーリー1.2: テスト容易性の向上**
        - **タスク1.2.1:** xUnitやNUnitなどのフレームワークを使用して、新しい最新のテストプロジェクトを作成する。
        - **タスク1.2.2:** すべての主要なサービス（例：`ISynth`, `IEventQueue`）に対してモック可能なインターフェースを実装する。
        - **タスク1.2.3:** すべての外部依存関係（FluidSynth、ファイルシステム）をモックして、コアロジックの真の単体テストを作成する。
        - **タスク1.2.4:** 既存の統合テストを、特定のタイミングやファイルの状態への依存を減らし、より堅牢になるように書き直す。

- **エピック2: Android UIの近代化と改善**
    - **ストーリー2.1: .NET MAUIへの移行 (Android)**
        - **タスク2.1.1:** `MidiPlayer.Droid` プロジェクトを .NET MAUI プロジェクト構造に移行するための調査を行う。
        - **タスク2.1.2:** .NET MAUI を使用してAndroid向けのUIを実装する。
        - **タスク2.1.3:** ネイティブライブラリ（FluidSynth）の参照が .NET MAUI プロジェクトで正しく動作することを確認する。
    - **ストーリー2.2: .NET MAUI UIのUX強化**
        - **タスク2.2.1:** パラメータ変更を効率的に処理するため、UIコントロールに「デバウンス」または「スロットリング」メカニズムを調査・実装する。
        - **タスク2.2.2:** パラメータが変更されたときにリアルタイムのフィードバックを提供するようにUIを更新する。

- **エピック3: ビルド管理**
    - **ストーリー3.1: CI/CDパイプラインの確立**
        - **タスク3.1.1:** GitHub ActionsまたはAzure Pipelinesのワークフローを設定する。
        - **タスク3.1.2:** 依存関係を復元し、すべてのプロジェクトをビルドするビルドステップを追加する。
        - **タスク3.1.3:** 新しい単体テストおよび統合テストスイートを実行するテストステップを追加する。
        - **タスク3.1.4:** ネイティブライブラリの更新方法を含む、ビルドと依存関係のプロセス全体を文書化する。

## 3. 段階的な実装スケジュール

改修は3つの異なるフェーズで実行されます。

```mermaid
gantt
    title MidiPlayer改修計画 (Android集中)
    dateFormat  YYYY-MM-DD
    section フェーズ1: 基盤整備とリファクタリング
    アーキテクチャリファクタリング :crit, done, 2024-08-01, 30d
    テスト容易性の向上      :done, after アーキテクチャリファクタリング, 30d

    section フェーズ2: Android UIの近代化と改善
    .NET MAUIへの移行 (Android)     :crit, active, 2024-10-01, 45d
    .NET MAUI UIのUX強化  : after .NET MAUIへの移行 (Android), 21d

    section フェーズ3: 自動化とドキュメント
    CI/CDパイプライン           : after .NET MAUI UIのUX強化, 30d
    最終ドキュメント      : after CI/CDパイプライン, 14d
```

- **フェーズ1: 基盤整備とリファクタリング:** コードベースの内部品質の向上に焦点を当てます。静的クラスをシングルトンにリファクタリングして適切なテストを可能にし、堅牢で最新のテストスイートを構築します。これは他のすべての作業にとって重要な前提条件です。
- **フェーズ2: Android UIの近代化と改善:** 安定した基盤の上で、まずUIフレームワークを.NET MAUIに移行し、アプリケーションの保守性と将来性を向上させます。その後、構築された新しいUI上でユーザーエクスペリエンスを改善します。
- **フェーズ3: 自動化とドキュメント:** 完全なCI/CDパイプラインを実装してビルドとテストを自動化し、品質改善が維持されるようにします。新しいアーキテクチャとビルドプロセスを文書化して完了します。

## 4. 主要なアーキテクチャに関する洞察

この分析は、いくつかの主要コンポーネントの役割を明らかにした優れた既存のドキュメントに大きく依存しています。

- **`EventQueue.cs`**: この静的クラスは、UIからバックエンドへの通信のコアであり、コマンドキューパターンを実装しています。その静的な性質がリファクタリングの重要な領域です。
- **`Synth.cs`**: このクラスはオーディオエンジンの心臓部であり、ネイティブのFluidSynthライブラリをラップしています。このクラス内の再生コールバックは、`EventQueue`メッセージが消費される重要なポイントです。
- **`Mixer.cs`**: このクラスはUIのViewModelとして機能し、UIの状態をオーディオエンジンから分離します。EventQueueと同様に、その静的な性質がリファクタリングの対象です。
- **UIロジック (`MainActivity.Component.cs` & `MainForm.cs`)**: UIファイルは、AndroidクライアントとWindowsクライアント間の機能の不均衡を明確に示しています。**今後の開発はAndroidに集中するため、`MidiPlayer.Win64` (`MainForm.cs`) は非推奨とし、開発を凍結します。**
- **テスト (`SynthTests.cs`)**: 既存のテストは、その脆弱性、システム状態への依存のため、テストアプローチの完全な見直しの必要性を浮き彫りにしています。
